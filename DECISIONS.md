# Architecture decisions

Answers to the five questions in `docs/requirements.md`. Paths are relative to the repository root.

## 1. AI integration

The chat code depends on one port, `AiProvider` (`apps/backend/src/ai/ai-provider.interface.ts`): `name`, `isConfigured()` and `streamChat(messages, { signal, messageId? })`, which returns an `AsyncIterable<string>` of text deltas (`messageId` is the assistant message id and is only used by the test decorator below). The implementation is injected through the `AI_PROVIDER` token (`apps/backend/src/ai/ai.constants.ts`), and `AiProviderFactory.create` (`apps/backend/src/ai/ai-provider.factory.ts`, wired in `ai.module.ts`) picks the adapter from the `AI_PROVIDER` env var. The three adapters (`providers/openrouter-ai.provider.ts`, `ollama-ai.provider.ts`, `gemini-ai.provider.ts`) extend `HttpStreamingAiProvider` (`providers/http-streaming-ai.provider.ts`), which owns the `fetch` call, failure mapping, abort handling and logging (provider, model, duration, outcome; never the key or the prompt), so each adapter only builds its request and names its parser. Swapping the provider is a configuration change (`AI_PROVIDER` plus that provider's variables); adding one means one class and one `case` in the factory, with no change to chat, history or controllers. Malformed output is handled by pure parsers (`providers/openrouter-stream.parser.ts`, `ollama-stream.parser.ts`, `gemini-stream.parser.ts`, sharing `providers/stream.utils.ts`): invalid JSON, an unexpected shape or an empty stream becomes `AiBadResponseException`, while an error object, a safety block or an HTTP 4xx/5xx becomes `AiProviderErrorException` and a refused connection `AiUnavailableException` (`apps/backend/src/common/exceptions/ai-*.exception.ts`). `ChatStreamService` (`apps/backend/src/chat/chat-stream.service.ts`) maps these, and timeouts, to a contract `ErrorCode` with a safe message that never contains provider text, and keeps the partial answer so Retry is possible. For end-to-end tests, `FaultInjectingAiProvider` (`providers/fault-injecting-ai.provider.ts`) decorates the real adapter only when `AI_FAULT_INJECTION=true` (set only by `docker-compose.e2e.yml`): a marker such as `[[e2e-fault:timeout]]` in the newest user message fakes one failure per assistant message id, and markers are stripped before any real call, so answers are never mocked and Retry reaches the real provider.

## 2. Streaming

Send, summarise and retry are `POST` requests that answer with `text/event-stream`. `ChatStreamService` runs every pre-stream check (session, Origin, ownership, validation, provider configured, no other stream running) so those still return normal JSON errors, then calls `reply.hijack()` and writes frames to the raw response through `SseWriter` (`apps/backend/src/chat/sse-writer.util.ts`): `message.created`, one `token` per provider delta, then `done` or `error`, plus a `: ping` comment every 15 s. The event schemas are in `packages/api-contract/src/sse.ts`; the backend validates each event against them only when `NODE_ENV` is not `production` and the frontend always validates. One `AbortController` per stream combines the client leaving, the first-token timeout and the total timeout: `watchClient` listens for `close` on `reply.raw` (with `writableFinished` false, because the request's own `close` fires once the body is read) and is attached right after the ownership checks, before the transactions, so an early disconnect skips the provider call and saves `aborted`; `stream-failure.util.ts` then picks `aborted` or `error / AI_TIMEOUT` from the abort reason. The content is saved once, at the end, together with `projects.updated_at` in one transaction that only applies while the row is still `streaming`, so a run that lost a race, or whose row `apps/backend/src/conversations/stale-stream.util.ts` already flipped to `error`, cannot overwrite a newer result. nginx proxies `/api/` with `proxy_buffering off` (`apps/frontend/nginx/default.conf.template`), and the browser reads the stream with `apps/frontend/src/features/chat/sse-reader.ts` and `stream-chat.ts` (`fetch` with a stream reader; a drop without `done` or `error` shows as a local `INTERNAL_ERROR`). I chose POST with `fetch` over `EventSource` because `EventSource` is GET-only, cannot send a JSON body and hides the body of a non-2xx response, so the JSON error envelope returned before the stream starts could not be read, and over a WebSocket because the traffic is one-way and already works through the proxy and cookie. Saving only at the end means fewer writes, at the cost of losing the in-memory text if the process dies mid-answer.

## 3. Conversation context

Every call starts with a system prompt from `buildSystemPrompt` (`apps/backend/src/chat/prompts.util.ts`): the CMF-assistant role and behaviour, then the project's title and description in a delimited `<project_context>` block and a line telling the model to treat it as information about the brief, not as instructions. Any `<project_context>` tags in the title or description are stripped first, so user text cannot close the block, and the prompt is rebuilt from the database on every call, so an edited description applies to the next message. The history is chosen by the pure `buildPromptMessages` (`apps/backend/src/chat/history-window.util.ts`): only `complete` messages count, the last `AI_HISTORY_MAX_MESSAGES` are kept, and the oldest are dropped until everything fits `AI_HISTORY_MAX_CHARS`; send and retry always keep the newest user message, while summarise only needs its instruction. If the latest stored summary falls outside the window it is pinned right after the system prompt, so long conversations keep their decisions. "Reset conversation" never deletes anything: `ConversationsService.reset` (`apps/backend/src/conversations/conversations.service.ts`) archives the active conversation and creates an empty one in one transaction, so the next prompt holds only the system prompt and the new message. Send, summarise, retry, reset and delete all take a row lock on the project first (`apps/backend/src/common/database/lock-project.util.ts`), so a reply can never be written into a conversation that was just archived or a project that is being deleted. The limit counts characters, not tokens, an approximation I accepted to stay provider independent.

## 4. State management

Server state and client state are split by lifetime. The TanStack Query cache holds everything that must survive a reload or be shared, including the message list (`apps/frontend/src/features/projects/projects-queries.ts`, `apps/frontend/src/features/auth/session-query.ts`), while Zustand (`apps/frontend/src/stores/chat-stream.store.ts`) holds only the transient parts of an in-flight stream: per project the assistant message id, the text so far, the phase and the `AbortController`. The specific decision is to keep streamed tokens out of the Query cache: writing it on every token would re-render the whole message list, so the cache receives only the structural events (`message.created` upserts the rows, `done` and `error` replace the row by id) and only `StreamingBody` (`apps/frontend/src/features/chat/streaming-message.tsx`) subscribes to the store, which a render-count test in `composer.test.tsx` checks. The stream is driven by a mutation in `apps/frontend/src/features/chat/use-stream-run.ts` that writes into the app-level QueryClient and store rather than the component, so navigating to another project does not abort it and coming back re-attaches to the store entry. Stop sets the cached row to `aborted` with the partial text at once, then `resyncAfterStop()` refetches at 300 ms, 1 s and 2 s (`apps/frontend/src/features/chat/stream-timings.ts`) and applies a server result only once the server no longer reports the message as `streaming`, because the server saves `aborted` only after it notices the closed connection; a row that still says `streaming` is never applied, the local `aborted` row stays, and the conversation is invalidated once more 5 s later. A new stream or a reset cancels the resync, and each await re-checks staleness, so a late GET cannot wipe new messages or revive an archived conversation. A `streaming` row that no local entry drives (another tab, a reload) shows the thinking indicator while `StreamingBody` re-fetches every 2 s until it is final.

## 5. What I would do differently with two more days

First, token-accurate history budgeting: `history-window.util.ts` counts characters, which can under- or over-fill a real context window, and I accepted that to keep the providers interchangeable. Second, load only the windowed history: `ChatStreamService` reads the whole conversation and windows it in memory, which is fine at demo sizes but should query the last N messages plus the latest summary. Third, cap chat streams per user (a rate limit or concurrency limit across projects): only sign-in is rate limited today and each stream costs provider quota, but I spent the time on getting the stream lifecycle and its races right first. Fourth, save partial content periodically instead of only at the end, so a crash loses seconds rather than the whole answer; I kept the simpler end-only write plus the stale-row recovery. Fifth, a browser for archived conversations (reset keeps them, but there is no UI or endpoint), left out because the brief only asks for reset. Sixth, run the Playwright suite in CI against a scripted provider: today `apps/e2e` runs on demand against the real stack and needs a live provider for the real-answer journeys. Seventh, a seed guard that refuses to run in production unless explicitly allowed, because the seed user's password is public; I documented `SEED_ON_START=false` instead, since the Compose stack runs in production mode for the reviewer. Last, smaller items: throttle Markdown re-parsing while a long answer streams, add token counts and request ids to the logs, and check at startup that the configured OpenRouter model exists, since free slugs are retired without notice.
